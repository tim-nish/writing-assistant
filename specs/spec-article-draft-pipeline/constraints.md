## Constraints

- Human attention budget ≤10 minutes per article (interview + verification passes); wall-clock time is unconstrained.
- Durability under a turn ceiling (added 2026-07-12; **resumption made automatic 2026-07-13** per #142): wall-clock is unconstrained but the turn/compute budget is not — the pipeline persists per-stage checkpoint state to the run workspace (`$WS`, building on the intermediates invariant below) and resumes from the last completed stage, so a turn-ceiling casualty is recoverable rather than a total loss. **Resumption is automatic, not opt-in**: on invocation the pipeline detects an in-progress run for the workspace and continues from the last checkpoint without the agent choosing to resume, and a large draft completing across multiple invocations is the normal completion model — a single realistic multi-source input is not required to finish within one turn budget. **The checkpoint unit is sub-stage for the long stages (amended 2026-07-18, #388)**: harvest checkpoints per pinned-source batch and stage 3 per filled section, and resume continues **mid-stage** from the last persisted boundary — a stage whose full cost exceeds one invocation budget still converges across invocations instead of replaying from its start. **The checkpoint unit also covers the Stage-2 gap-interview elicitation loop (amended 2026-07-22, #533):** harvest itself is **capture-only and non-interactive** — its §4 NEEDS-OWNER collection presents no question loop — so the interruptible elicitation is the **Stage-2 gap interview** (`cmd_interview`), which the per-pinned-source-batch harvest boundary did not cover; an ESC-then-resume during the interview replayed earlier work and burned a large token volume (#533). Stage 2 now persists its question-loop state (questions presented, answers captured, questions remaining — building on the #234 interview-journal payload record) as a sub-stage checkpoint (`cmd_substage`, the same mechanism the harvest per-source batch and stage-3 section use), so a resume **re-enters at the next unanswered question**, never re-asking answered questions. Each stage surfaces a budget-triage signal before hard failure, and that signal is an **orderly stop, not an advisory**: on breach the stage persists at the next sub-stage boundary, records the partial-progress note (CAP-6), and exits clean — `error_max_turns` or a wall-timeout is a defect of the stop mechanism, never the normal end of an over-budget run. **The orderly stop binds identically on resumed invocations (amended 2026-07-22, #533):** budget triage is not a fresh-run-only path — a resumed run enforces the same orderly stop, and a resume that would redo significant work (a cache or checkpoint miss) **discloses in one line what it will re-do and why before spending**, so a resume never silently re-burns a budget (per SPEC-writing-assistant's enforced-mechanism invariant).
- Per-stage round-trip economy (added 2026-07-13 per #142): the turn/compute cost of a stage is a first-class constraint — a stage folds its mechanical checks into as few script invocations as its contract allows (e.g. config validation, path resolution, and source enumeration are not separate round-trips when one can carry the others), so a realistic multi-source run makes measurable progress per turn rather than exhausting the budget on orchestration overhead before any reviewable output exists.
- Validator convergence (added 2026-07-15 per #206): an agent-facing mechanical validator must make acceptance reachable without trial-and-error — for every rejectable form there is a sanctioned tooling path that **emits** the accepted form (e.g. the pin helper emits entry-ready `CLAIM / SOURCE / KIND` lines carrying the pinned pointer and the verbatim source text, so quotes and pointers are copied from tool output, never re-typed), and the stage builds entries through that path inside the writing loop, making the validator run a confirmation pass rather than a search procedure. A repair loop against a mechanical validator is bounded at **two passes**; a breach surfaces as the stage's budget-triage signal — never further loops — and entries still rejected route to NEEDS-OWNER per the existing partition rule.
- No invented evidence (amended 2026-07-11): sourced claims carry pointers; derived claims may compress, combine, or restate named fact-sheet inputs — inheriting their pointers — but must not introduce new causality, significance, evaluation, comparison, intent, or scope; narration asserts nothing checkable (falsifiability test: no reviewer with source access could mark it false); every other assertion carries `[VERIFY]`. The pipeline never silently asserts, and the drafting agent never grades its own claim/narration boundary — `verify-provenance` runs independent of the drafting context, **in a subagent that never saw the drafting turn** (NFR13; the same isolation the CAP-7 rubric judge inherits).
- No confabulated NEEDS-OWNER premise (added 2026-07-21, #526; **restated 2026-07-22, #567, as the NEEDS-OWNER instance of the engine-wide gate-item content-grounding constraint** — SPEC-writing-assistant Constraints: a machine-authored gate item asserts no factual premise without a resolvable pointer or an inline `unverified —` marker at the point of use. This clause is that rule's item grammar for the NEEDS-OWNER path, **never a narrowing of it**: the declared `premise:` clause survives as the structured form, and an **inline `unverified —` marker at the point of use** is accepted alongside `premise: unverified`. The rule attaches to **premise clauses wherever they appear in the item, including subordinate clauses** — the `not in declared sources` top-level disclosure is not a defence, which is exactly the #526 shape): a NEEDS-OWNER item may pose an **unsourceable question** — that is precisely why it is on the list — but it must never **assert an unsourced factual premise as established fact**. Any factual setup a NEEDS-OWNER item carries is expressed as a **declared `premise:` clause** that is EITHER pointer-backed under the same resolvable `file:line@commit` grammar as a fact-sheet SOURCE, OR explicitly marked `premise: unverified`; an undeclared premise smuggled into the CANDIDATE prose, or a declared premise that is neither pointer-backed nor `unverified`-marked, is a **named validator rejection**. The item's *question* stays unsourceable-by-definition; only its *factual ground* is constrained. This mirrors the seam's own contract (SPEC-policy-source-seam CAP-3 / `validate-interview-items.py` R3–R4: a seed carries a pinned pointer, a confirmation-shaped item is rejected) and applies the no-invented-evidence principle to the NEEDS-OWNER path: harvest assembles evidence and the interview is the judgment gate — a NEEDS-OWNER premise is evidence, not license to invent the factual ground an owner might ratify while skimming a plausible "described internally as…" clause. The `not in declared sources` disclosure covers the *question's* unsourceability, never license to invent its factual setup. Enforced **in lockstep** at `scripts/validate-needs-owner.py` and `skills/harvest/SKILL.md §4` — a change to one without the other is a defect (the same lockstep discipline the nine-KIND set carries).
- A section needing more than one rewrite routes back to a new interview question, never into open-ended editing; quality-gate revisions (CAP-7) are likewise bounded — two cycles, then a publish blocker, never open-ended iteration. The second cycle is a **bounded delta re-check** that cannot introduce a new interpretive dim1–2 judge finding (#349), so the two cycles converge rather than oscillate on freshly-interpreted findings.
- Missing-input repair route (added 2026-07-18, #348): a review or quality-gate finding classified **missing-input** — an evidence gap the draft cannot fix in prose (insufficient evidence, a missing example/episode, an unsupported narrative claim), as distinct from a writing-problem (structure/prose) finding — may route back **one bounded hop** to a **scoped re-harvest** (a narrowed source set) **or a single bounded owner-elicitation question**, then re-enter the pipeline with the new material. This is the ONLY backward edge to harvest/interview beyond the rewrite route above, and it is governed by the **same bound**: it counts against the same two-cycle limit, and an unrepaired missing-input finding becomes a **publish blocker** rather than a third hop — never open-ended re-harvest. The classification of a review finding as writing-problem vs missing-input is SPEC-article-review's contract; the pipeline never silently re-harvests, and each hop respects the ≤10-minute owner-attention budget (a re-harvest is scoped and pinned; an elicitation is one owner-facing question under the proposal contract). Evidence gathered on a hop is harvested and pinned exactly like any Stage-1 fact — a policy line never becomes a SOURCE, and the no-invented-evidence rule is unchanged.
- Per-section minimum evidence type (added 2026-07-19, #413/#414): at the stage 3→4 boundary the pipeline checks each filled section against the minimum evidence TYPE its framework declares (`episode | example | measurement | none` — the declaration is SPEC-article-frameworks' contract, authored with the templates) as a **stage-progression precondition beside CAP-7**. A section whose declared type is absent is **never silently backfilled with unrelated factual material and never reported as success**: it classifies as a **missing-input** finding and takes the repair route above, under the same two-cycle bound. On that hop, the pipeline constructs candidate **episodes** from already-captured event facts — grouped events plus a one-line narrative frame plus the constituent source pointers; harvest itself stays capture-only and gains no extraction logic — and presents them for **owner selection** as the hop's single bounded elicitation question; a selected episode enters the fact sheet pinned like any harvested material. An unrepaired evidence-type absence surfaces as a **publish blocker naming the section and the missing type** (CAP-6). **Carrier RE-ANCHORED, unrunnable case a NAMED STATE (amended 2026-08-02, #1288 — see `amendments.md`).** The fact sheet this check resolved KINDs against died with harvest (#1182/#1224); the carrier is now `$WS/examination-pins.txt` read beside the provenance map, and independently of that re-anchor's reach the check reports its own state as `cannot-determine — <reason>`, never silence and never a pass.
- Interview questions (CAP-2) and owner-verification items obey SPEC-writing-assistant's **owner-facing proposal contract**: each shows where the item lands in the article (outline context + short section preview), why it is asked, and choices stating their concrete effect on the article — the owner answers from repository knowledge alone, never by inferring the generation logic.
- Policy seeding (added 2026-07-14, SPEC-policy-source-seam): the optional `policy_source` read seeds candidate **questions only** — it never supplies, pre-fills, or recommends an answer to a factual gap, and triage/recommendation generation remain a view over harvest output; the single bounded exception (added 2026-07-18, SPEC-policy-editorial-direction CAP-6) is a **recommended default for an editorial-judgment gap** (`opinion`/`significance`/`surprise`/`tradeoff`/`warning`/`audience`): recalled from the policy surface and owner-ratified (approve/modify/replace/skip), it counts against the ≤5 cap, keeps `owner_answer` empty at generation, and never lets a policy pointer become a SOURCE — an ineligible-class or tension-item default is a named validator rejection; seeded questions share the ≤5 budget (they displace, never extend it), and **one slot is reserved** (amended 2026-07-17, #302): when at least one valid policy-seeded tension item survives validation, the highest-priority one is guaranteed a slot — it displaces the lowest-priority survivor, never extends the cap — so the editorial anchor (SPEC-policy-editorial-direction CAP-2) and the staging-candidate emitter (SPEC-policy-source-seam CAP-4) are never silently starved by a long NEEDS-OWNER list; a missing or unusable policy source degrades to the generic interview with at most one logged line — never a failure. **The ≤5 cap and the #302 reserved slot govern only NEEDS-OWNER candidates and policy-seeds (amended 2026-07-22, #542/#545):** pipeline-**mandated/gate** items — the CAP-8 depth offer, the audience declaration (#1283) and the CAP-7 config↔policy **reconciliation** gate — are **not** interview candidates and do **not** compete for these slots; they are a **separate presentation tier, guaranteed outside/before the capped NEEDS-OWNER set**. In particular a reconciliation gate item **never consumes the #302 reserved policy-seed slot** — so #302's guarantee to the highest-priority policy-seeded tension item holds whenever one survives validation (the #545 failure, where `rc1` took the reserved slot and starved a valid `p1`, cannot recur). Enforced at `scripts/draft-pipeline.py` (`cmd_interview` selection) and `skills/draft-article/SKILL.md`.
- Interview `skip` is captured as a disposition only (added 2026-07-11, `docs/interview-architecture.md` D2): its effect on the target slot — omission, deferral, accepting the recommendation later, `[VERIFY]`-marked inference, or a publish blocker — is the framework slot's declared contract (SPEC-article-frameworks), never an interview-engine default; the skip choice's label states that slot's declared effect.
- Consumes the framework templates from SPEC-article-frameworks verbatim; category structure is not redesigned per run.
- Implemented as a Claude Code skill (`.claude/skills/`) so harvest can read the repo directly.
- All intermediates — fact sheet, NEEDS-OWNER list, interview answers, provenance map, quality-gate judge output, scratch — are written to the run's workspace resolved by the path resolver (`docs/storage-architecture.md` D1–D2), never into the host repository's working tree; the location is a stated contract, not an agent default. Only declared products land in the host repo, at `output.drafts` (SPEC-writing-assistant footprint invariant). **The declared products are two (amended 2026-07-18, #361/#362): the canonical draft `drafts/{slug}.md` and the article plan `plans/{slug}.md` — the draft flow persists both before reporting completion, and a failed write of either is a hard error (the run never reports "complete" with a workspace-only canonical). Platform variants are not draft-flow products; they are emitted by the separate post-review variant invocation (CAP-4).** **Beside the two gated products, the destination repo carries exactly one regenerated, NON-GATING view (amended 2026-07-22, #550): `INDEX.md`, the browsing surface the repo itself declares "regenerated — one line per backlog/draft/newsletter item".** It is a deterministic projection over the item frontmatter the pipeline just wrote — **the files always win**, regeneration is idempotent, and it is **not completion-gated**: a failed index write is a **disclosed warning** in the completion summary, never the hard error the two products carry. This is the whole permitted write surface in the destination repo — two gated products plus this one view — and it is **mechanically bounded** by the footprint check, which covers the destination repo, not only the host (`scripts/check-footprint-invariant.sh`). The **site tree remains untouched**: `pipeline-proposes, owner-commits` governs the owner's website (owner decision record 2026-07-16 site-record modeling; 2026-07-18 site-projection constraints), **not** the `output.drafts` destination repo, which is the pipeline's own declared product destination.
