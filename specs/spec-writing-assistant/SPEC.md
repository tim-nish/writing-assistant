# Writing Assistant plugin repository

## Why

An opportunity to capture plus a vision to realize: the article specs already produced in this repo (frameworks, draft pipeline, review) are valuable beyond the website repo, but as `.claude/skills` candidates inside one repo they can serve only that repo. Extracting them into a standalone repository packaged as a Claude Code plugin makes the assistant installable per-repository — so drafting an article about QuantScenarioBench runs *inside* QuantScenarioBench with direct access to its specs, docs, and git history (which is where the draft pipeline's harvest step needs to be). The engine/identity split keeps an open-source release cheap if dogfooding on research-notes proves the tool out.

## Capabilities

- **CAP-1**
  - **intent:** The assistant is a standalone git repository installable as a Claude Code plugin on a per-repository basis; the repo serves as its own marketplace via `.claude-plugin/marketplace.json` (`/plugin marketplace add <owner>/<repo>` + `/plugin install`), with Community Marketplace listing an optional later step for discoverability only.
  - **success:** Installing the plugin in a fresh clone of QuantScenarioBench makes the drafting/review commands available there without copying files into that repo and without any marketplace submission or review.
- **CAP-2** (amended 2026-07-17, #301 — typed sources)
  - **intent:** A harvest step gathers facts from the host repo and any additional sources declared in a per-repo `writing-sources.yaml`. Source entries carry a `type` — `path` (the default; local paths, sibling repos such as research-notes), `github-issues` (the host repo's issues, optionally label-filtered), or `tanuki-den` (read-only access to the target's findings ledger) — with every fact carrying a resolvable source pointer: file/line pinned to a commit, a commit, a URL (the native form for issue facts), or `den:<ledger-id>@<run>` for Den findings. Recurrence counts and dispositions on Den/issue facts are data the pipeline may quote, never judgments it may amplify; the reads are one-way — harvest never writes back to the Den or to issues.
  - **success:** A harvest run against QuantScenarioBench with research-notes declared as a source produces a fact sheet whose every entry resolves to an exact location in one of the two repos; undeclared repos, undeclared source types, and any producer state not named by a declared entry are never read.
- **CAP-3** (amended 2026-07-11 per `docs/harness-architecture.md`)
  - **intent:** The draft pipeline (SPEC-article-draft-pipeline: harvest → ≤5-question interview → framework fill with `[VERIFY]` markers → article-quality gate → platform variants) runs as a plugin skill inside the host repo.
  - **success:** The pipeline's existing success criterion holds when run from a non-website repo: draft in ≤10 minutes of owner attention, zero unmarked invented claims, and the draft passes the article-quality gate (SPEC-article-draft-pipeline CAP-7).
- **CAP-4**
  - **intent:** The review workflow (SPEC-article-review: lint → structure → prose → cold read, capped severity-tagged findings) runs as a plugin skill against a draft file in the host repo.
  - **success:** Each pass runs once per draft version and emits findings, not rewrites, per that spec's contract.
- **CAP-5**
  - **intent:** The four article frameworks (SPEC-article-frameworks) ship as plugin assets the pipeline fills verbatim.
  - **success:** A produced draft's structure matches the chosen framework template slot-for-slot.
- **CAP-6**
  - **intent:** Owner identity (name, site URL, pointer-block content, canonical/syndication policy, frontmatter schema of the target site) lives in a user config file, not in skill prompts, so the engine is generic.
  - **success:** Deleting the owner's config and supplying a different user's config produces drafts carrying the new identity with zero skill-file edits; grepping the skills for `tim-nish.dev` returns nothing.

## Constraints

- Must run inside any host repository without assuming the website repo's layout; all host-specific knowledge enters via `writing-sources.yaml` (machine-global per-repo config, amended 2026-07-15 per #211 — see the footprint invariant) and the user config.
- Draft output location is declared per host repo in `writing-sources.yaml`; the pipeline never assumes a fixed `drafts/` path. `output.drafts` may name a destination **outside** the host repo (amended 2026-07-15 per #211) — an external private articles repository is the recommended default, so article products (private assets) never enter a maybe-public host repo's history.
- Publication boundary (added 2026-07-15 per #211): repository boundaries follow publication boundaries — the plugin never causes a private pointer (a `policy_source` path, a private article destination, machine-local layout) to be committed into a host repository, because a host repo may be public or become public later and removal costs history scrubbing. Everything carrying such pointers lives in machine-local configuration. **This repository is itself a public artifact, and the rule binds it too (added 2026-07-26 from triage #731 — previously implicit).** The invariant above was written about *host* repositories; `scripts/check-publication-boundary.sh` has enforced a broader rule all along — rule A follows provenance **values** through the complete tracked tree (`:118-123`), rule B rejects hub-name and layout literals under `specs/` (`:125-138`) — and that broader rule was stated nowhere, so its only expressions were the check and an owner decision record (2026-07-15, tanuki open-sourcing: the boundary runs *through the spec content*; the generic mechanism is public, provenance and owner-specifics stay in a private file). It is now written down: **no artifact tracked in this repository carries the recall hub's name, its file layout, or a real commit pin** — not spec text, not scripts, not fixtures, not docs.
  - **The grounding pin is two-tier (#731).** A claim about what the served surface records still requires a consult, and the consult still binds the claim — but the pin **splits at the publication boundary**. The **public** half is a generic decision line carrying the date and the title of what was consulted (`owner decision record — YYYY-MM-DD (short title)`), which is enough for a reader to see *that* a decision grounds the claim and *which*; the mechanism is public. The **private** half — the hub name, the commit pin, the file:line set — is machine-local, outside every repository, and is where verification actually happens. Withholding only the address is the boundary's own wording, not a new concession.
  - **Declared precedence, because the private half is a conformance copy.** On mismatch the **private record wins** and the public decision line is the defect. A public line with no private counterpart is unverified and must carry the explicit `unverified —` marker at the point of use, under the gate-item content-grounding rule below; it never reads as a grounded claim.
  - **Write clean; do not scrub (the load-bearing half).** Remediation of an existing leak is **conversion at the next edit**, never a scrubbing sweep, and never history rewriting. The reason is recorded and is not a preference: scrub-at-publication cannot be clean — this portfolio has already produced one instance where a sibling repository's tracked content was scrubbed while its git history still carried the pre-scrub pointers, on a repository that was already public (owner decision record — 2026-07-26, scrub-at-publication is never clean). A scrub therefore buys the appearance of cleanliness rather than the fact, and spends effort that writing clean would not need. The obligation this states is **prospective and absolute**: a new leak is a defect at the moment it is authored, and the check is its enforcement layer.
  - **Known cost, stated rather than assumed away:** a reader of the public tree can no longer verify a grounding claim independently — only the owner can. That capability was never actually available to a reader, since the hub was always private; what changes is that the text now says so instead of implying otherwise with a pointer nobody outside could resolve.
- This repo is self-contained: the three adopted article specs are vendored under `specs/`, the canonical home for implementation specs. Changes to the adopted specs are made in the vendored copies here; the website-repo originals are superseded for this project.
- The three article specs are adopted contracts: this repo ports them to plugin form but does not redesign their internals; behavioral changes go through their own spec updates first.
- No JavaScript/TypeScript anywhere in the plugin: skills, commands, and templates are Markdown; helper scripts are Python (stdlib-only — host repos guarantee no venv or installed dependencies) or POSIX shell. Invoking `npx bmad-method install` as an external tool does not violate this.
- The repository is BMAD-managed from day one (specs + epics + stories), since the owner implements via BMAD.
- BMAD artifacts and hand-written content stay strictly separated: BMAD's footprint is exactly `_bmad/`, `_bmad-output/`, and `.claude/skills/bmad-*`; project specs live only under `specs/`. Release stripping is then a mechanical removal of those three paths with no judgment calls — nothing hand-written may ever land in a BMAD directory, and no BMAD output may land in `specs/`.
- Dogfooding gate: OSS release decisions wait until the plugin has produced real published articles for research-notes/QuantScenarioBench; releasing is a separate later decision, not part of this build. If working-note history must not ship, release happens via a fresh public repo (or squashed export), keeping this BMAD-managed repo private.
- **Target-repo selection** (added 2026-07-17, #309): every entry flow resolves the host repository through one rule — explicit `--root` wins unconditionally, else the git top-level of the current directory, else **fail closed** (exit 2 with a pass-`--root` diagnostic; never a silent cwd fallback) — with both branches realpath-canonicalized, and exactly **one resolved root per run**: no script step (entry gates included) may consult raw process cwd as a side channel. The resolved target path appears in each flow's **first owner-visible output**, before any scope read, workspace mint, or LLM spend; when an explicit `--root` and cwd's git top-level both resolve and differ, a one-line informational notice names both (explicit still wins, fail-open).
- **Host-repo footprint invariant** (engine-wide; added 2026-07-11 from dogfood findings, `docs/storage-architecture.md` D1–D2): the plugin never writes state or intermediate artifacts into the host repository's working tree — the only files it creates there are declared products at `output.drafts`. All storage paths (config lookup, state root, per-run workspaces) resolve through a single stdlib-Python path-resolver helper; no other script, skill, or prompt carries a storage-path literal, so the layout behind the resolver is an implementation detail with one migration point. **The O1 exemption is removed (amended 2026-07-15, #211 — `docs/storage-architecture.md` O1 resolved to machine-global per-repo config):** `writing-sources.yaml` resolves from `~/.config/writing-assistant/repos/<repo-key>/` through the resolver, no in-repo file exists, and the invariant is now total — the plugin writes nothing into a host repository except declared products at `output.drafts`, and `output.drafts` itself may point outside the host. Article plans at `plans/<slug>.md` in the articles repository are a declared product of that destination (added 2026-07-17, #310, SPEC-article-plan) — never a file in the host source repo. During migration, a legacy in-repo `writing-sources.yaml` is still read (machine-global wins when both exist) with a one-line deprecation pointer to the migration path — never silently, never forever. **The destination repo's permitted write surface is named exhaustively (amended 2026-07-22, #550):** at the `output.drafts` **destination** repo — which the lint and footprint check name explicitly, never "host repo" — the plugin writes the **two gated products** (canonical draft, article plan) **plus exactly one regenerated, non-gating view** (`INDEX.md`, SPEC-article-draft-pipeline). Nothing else, and a write outside that set is a footprint violation the check names. **Working-note renderings are ordinary `output.drafts` variant files (corrected 2026-07-24, #658 — the earlier same-day #653 amendment overreached and is withdrawn):** a working-note's email and web-archive renderings are variant files landing at `output.drafts` like every platform variant (already permitted — `SPEC-platform-variants`: "only the variant files land at the `output.drafts` destination"), **not** a new destination product. The plugin does **not** write the published **`newsletter/` section**: that section is an owner publish target — `pipeline-proposes, owner-commits`, lowering is a human act (`consulted: hub@<private-pin> topics/articles.md:52,60`) — and a profile's `newsletter/` `layout.dir` is a conformance record of that target (like Zenn's `articles/`), never a plugin write location. The permitted destination write surface is therefore **unchanged** from #550 above. This does not loosen the host-repo invariant above (a host *source* repo still receives nothing), and it does not reach the owner's **site tree**, which the pipeline never writes — `pipeline-proposes, owner-commits` is site policy, and the destination repo is not the site. **A test-declared run never writes to a destination it does not own (amended 2026-07-22, #573; predicate corrected same day at re-triage):** a run that declares itself a test — the `--allow-external-draft` check-harness escape — is refused when the resolved `output.drafts` lies **outside the system temporary directory**, i.e. outside the run's own disposable tree; the run supplies an explicit `--out`, or it aborts naming the destination it refused. A destination **inside** that tree resolves normally. The predicate is the **destination**, not the invocation shape: the first formulation refused config resolution for any test-declared run, which also made the #213 `--create-out` consent path untestable (`scripts/check-stage5-variants.sh:190-211` must resolve a config destination with no `--out` — that *is* what it tests). **Known limit, accepted deliberately:** "under the system temp dir" is an OS path convention, so a harness using a non-temp scratch directory is refused for a reason unrelated to the leak; fixtures live under the temp tree. The `output.drafts` destination is a **machine-wide** resource that reads as a per-run one, so it is isolated rather than shared silently (`policy: a shared-scope resource that presents as private must be isolated OR warn loudly on collision — silence is not among the options`, the hub `topics/claude-code-ops.md:9`). The observed leak path is not a temp host — every temp host resolves its own tree — but the **plugin's own development repo**, which is a configured host whose destination is the owner's real articles repo, so an unrooted test invocation from it writes a real canonical. **The NEEDS-RECORDING artifact is RETIRED, and the #1083 resolution is retracted with it (amended 2026-08-01, #1183).** The #1083 amendment kept the artifact and moved its default to the tracker form, leaving the file append available as an owner-consented act; **both branches are now removed, and with them the host-repo join that produced the gaps.** The retraction is not a change of mind about the footprint invariant — that invariant is **unchanged and still total** — but about the mechanism the exception was being sought for. Two grounds, neither of which existed at #1083. **First, the join never established its substrate:** `journey_join` matched a hub lesson's filename stem against the concatenated text of the repo's declared `journey:` files, and where no such block is declared it searched **zero bytes** and stamped every element `episodic-unrecorded` anyway — an asserted absence over an empty haystack, which is `cannot-determine` under the three-valued absence rule this spec already carries (#1181, five false tracking issues minted from it). **Second, the join had no natural producer:** its key is another repository's internal filename stem, so no document written for its own purpose can contain it, and the only text that could ever satisfy the join was the IOU the gap step itself wrote — a to-do that discharges itself. **The same-run flywheel condition is therefore retracted, not merely relaxed** (it rested on `owner decision record — 2026-07-24 (topic-map evidence terrain)`, whose premise was that emitted gaps were real). A mechanism whose gaps are artifacts of its own broken lookup mints no backfill worklist. **The prohibition is carried by removing the writer, never by a rule anyone must remember** — a check asserts the absence of any code path writing `docs/journey.md`, in the shape `check-footprint-invariant.sh` already uses, because a prohibition is violated at the tool boundary and prose there is advisory (`consulted: hub@<private-pin> LESSONS.md:70, LESSONS.md:28`). **What survives, and why:** `episode.served` / `episode.arc` — the hub serving a Strand's journey arc — is untouched. It was never the defective half; the defect was the host-repo join reporting an absence beside it. The gap step's remaining duty shrinks to a **scope statement** over the selection (which Strands have a repository bound to them and which do not), which is a fact about the selection rather than an absence claim about the owner's repo, and mints no work items.
- **Owner-facing proposal contract** (engine-wide; added 2026-07-10 from dogfood findings): every prompt that asks the owner to approve, modify, or decline something — gap-interview questions, owner-verification items, review-arbitration findings, visual proposals, and any future proposal surface — must show (a) **where** the item lands in the artifact (outline/section context, with a short preview of the current content when one exists), (b) **why** it is being asked, and (c) choices whose labels state their **concrete effect on the artifact** — never shorthand labels that require inferring the generation logic. A first-time user must be able to answer from repository knowledge alone, without already understanding the generated draft. Additionally (added 2026-07-11, `docs/interview-architecture.md` D4): (d) **selective presentation is the primary interaction model** — every proposal surface presents choice-based selective prompts, with free-form text entry appearing only as the input mode for owner-only knowledge (open interview questions, modify/replace paths); collecting answers as free-form text where choices are mandated is a contract violation, not a presentation preference; and (e) **payload integrity is validated before presentation** — every item's where/why/effect fields present, non-empty, and untruncated, with content fitting its display budget by authorship (re-written shorter), never by clipping; a validation failure blocks presentation the way `verify-markers` blocks stage progression. Stage specs reference this contract; they do not restate it. **The contract needs a CARRIER, and (d) is where it kept breaking (amended 2026-07-31, #1081).** Clause (d) has said since 2026-07-11 that collecting answers as free-form text where choices are mandated is a *contract violation, not a presentation preference* — and two gates in one dogfood sitting were nonetheless rendered as chat prose, the owner not recognising that the system had stopped and was waiting. Both already had the option lists a selector needs, so nothing was missing but the rendering, which is the tell that the rule had no carrier. **A rule is enforced only at the layer where it can be broken**, and that layer here is the agent's own composition step, which this product does not own — so a rule written in a skill file or in this spec is *advisory, real, worth writing, and NOT a carrier* (owner decision record — 2026-07-28 (the conversation layer cannot get a mechanical carrier inside the harness)). **The carrier therefore goes at the last boundary this repository controls: the composed artifact.** A surface that asks the owner anything emits its question as a MACHINE-READABLE payload — the option list, each option's effect, and the free-text channel — and the rendering step **quotes** that payload into the host's selection UI rather than composing prose from it. This is the CONSTRAIN ordering of the register clause below, applied to gate SHAPE rather than to gate wording: text assembled from a ratified payload leaves no free-form question for a reply to bury. **The absence is what is checkable**, since an obligation produces no event to hook: a surface that reaches the owner with no emitted question payload is the visible-absence signal, and that is what a check asserts — never the prose of any particular reply, which nothing here can read. **This is the fourth instance of one property**, after a pending item missed, a decision ratified unread, and a designed pause experienced as a silent stall (owner decision record — 2026-07-24 (fork-prompt gate rendering)); the root cause is the same each time — *the surface did not read as the gate it was*.
- **Enforced-mechanism invariant** (engine-wide; added 2026-07-22 from triage #534/#533): any **budget cap, cache, or checkpoint** the engine *promises* is enforced by a **mechanical assertion**, never by per-prompt compliance alone — caps and caches are architecture, not prompt hygiene. A run that reaches its completion summary while a promised mechanism did **not** execute (e.g. a completed harvest whose blob-keyed cache was never populated, #534) **fails loudly and names the omission** — a silently-skipped mechanism that leaves a valid-looking product is a defect, not a warning. Correspondingly, **each interruptible stage declares its interruption/resume contract**: the state it checkpoints, where a resume re-enters, and that the budget-triage **orderly stop** (SPEC-article-draft-pipeline durability constraint) binds **identically on resumed runs** and **discloses re-done work before spending** it — an interruptible stage without a stated resume contract is the same class of gap as an uncapped fan-out. Harvest states its contract first (SPEC-article-draft-pipeline CAP-10 + durability constraint); other stages state theirs as they are hardened. The mechanical assertion enforcing a promise is authored **in lockstep** with the prompt/skill step that describes it — a change to one without the other is a defect (the same lockstep discipline the fact-sheet KIND set carries).
- **One frontmatter-value reading** (engine-wide; added 2026-07-25 from triage #713): a frontmatter **value never carries a trailing `#` comment** — the comment is documentation for a human reading the file, never part of the datum — and every reader in the engine returns the same value for the same field. Stated as an invariant because the alternative was already shipping: `draft-pipeline._read_frontmatter` **kept** the comment while `resolve-user-config.load_yaml` (what `lint-article`, `resolve-platform-profiles` and `topic-map` use) **stripped** it, and both are called from inside the same modules — so which value a check saw depended on which helper its author happened to reach for. **The cost was a dead contract, not a cosmetic split:** SPEC-canonical-adaptation CAP-1's same-reader precondition is an equality test against `audience_id`, and every canonical the engine writes carries `audience_id: en-practitioner   # pipeline-internal compatibility id …` (`scripts/render-frontmatter.py`), so the test compared `'en-practitioner'` against a comment-bearing string and was **always False** — verified 2026-07-25: `adapt-canonical.py plan --slug tanuki-honest-automation --target devto`, a same-reader same-language target, returned a plan skeleton with exit 0 where the contract requires a refusal. **Per-call normalization is not the remedy**: story 18.112 normalized locally for `generated_by`, and generalizing that makes correctness depend on each author remembering, where forgetting fails **silently** as a plausible mismatch — the shape the served surface names, "a value written in good faith into a file the system reads and then ignores for that key is indistinguishable from one that took effect, and the divergence surfaces later as 'the feature does nothing' with no thread back to the cause" (`consulted: hub@<private-pin> topics/knowledge-architecture.md:77`). **Known cost, stated:** a value whose data legitimately contains `#` is truncated; `load_yaml` already had that exposure, so this equalizes rather than introduces it. **Explicitly not decided here:** whether `render-frontmatter` should emit those trailing comments at all — they serve a human reader, removing them is a separate call, and this invariant makes the split harmless either way.
- **Gate-item content grounding** (engine-wide; added 2026-07-22 from triage #567, ratifying #526's fix as a general property): the owner-facing proposal contract above binds gate-item **content**, not only its form. **A machine-authored gate item asserts no factual premise without a resolvable pointer, or an inline `unverified —` marker at the point of use.** A well-formed option carrying an invented premise passes every structural check and still corrupts the ratification, because the owner ratifies the *content* — the failure mode is an owner skimming a plausible "described internally as…" clause and ratifying an invention, so the judgment the gate captures is about a world that does not exist. Three properties are load-bearing: (a) the **marker spelling is `unverified —`, inline, at the point of use** — never a footnote the reader may skip, and deliberately the same spelling adopted for unverified operational references, decided once across both surfaces rather than twice; (b) the rule attaches to **premise clauses specifically, not to an item's overall honesty** — #526's item disclosed correctly at the top level (`not in declared sources`) and still smuggled a fabrication into a subordinate clause, so top-level candour is **not a defence**, and an honest top-level disclosure can actively make the invention read as licensed; (c) a **pointer-carrying** premise validates under the same resolvable `file:line@commit` grammar as an evidence entry. This binds **every** machine-authored gate item — NEEDS-OWNER items, interview items, fork-gate candidates and FYIs, proposal payloads, review-arbitration findings, visual proposals, and any future proposal surface — and is the third artifact class of one rule (spec bindings → reported references → gate premises). Per-surface specs state their **instance** of this constraint and its validator; they do not restate the rule, and they may not narrow it.
- **Owner-surface register** (engine-wide; added 2026-07-28 from triage #858/#857): the owner-facing proposal contract above binds a prompt's *form* and the clause above binds its *premises*; this binds its **register** — whether a first-time owner can read it at all. **The recurring defect is register, not vocabulary, and the remedy shape is what has been wrong.** Six applications of one fix class (#233, #646, #673, #790, #842, and the 2026-07-28 terrain screen-1 dogfood) each extended an enumerated denial list scoped to the surface where the last leak appeared, with the recurrence count climbing throughout; persistence through fixes is evidence about the **attribution**, not about the dose. The discriminating measurement: of the three 2026-07-28 leaks, **0 of 3** were catchable by any extension of `INTERNAL_VOCAB` / `FORBIDDEN_MARKERS` / `check-retired-vocabulary.sh` — one was ordinary English stating contract invariants to a reader who has never seen the contract, one was the product's own first-class term, one was a state dump of a validator's intermediate made of the product's own data. None contains a token to list. Four properties bind: (a) **the enumerated-denial remedy is prohibited as the response to a register leak** — a denial list's non-member fallback is *admit*, so the defect is in the shape rather than in any list's contents, and you cannot subtract your way into a different register; (b) the existing denial lists are **demoted, not deleted** — they keep their real role as a cheap deterministic first pass, and what is removed is the premise that extending them is the response; (c) **the remedy is ordered CONSTRAIN → DETECT → ENUMERATE, and the ordering is the content** (corrected 2026-07-28 from triage #857, superseding this clause's own first form the same day): **CONSTRAIN** wherever owner-facing output can be assembled from ratified material — the **default**, and where the leaks in evidence live; **DETECT** only where free composition is irreducible, and there the move is to **shrink that surface** by routing content through the constrained path rather than to police it better; **ENUMERATE** only as a fast path beneath both. What this clause first said — that the repository-knowledge-alone test (`skills/owner-facing-proposal-contract.md`) is applied as a *positive* admitting property, discharged once at composition — is **demoted to the DETECT fallback, not deleted**: an admission gate is *"post-hoc detection with a better predicate, not a change of shape … text is still composed freely, then inspected, then admitted, which is the blocklist's own shape one level up, failing the same way with a longer tail"*. Moving the check to one seam and from negative to positive were both real gains, and they survive as the seam's **location**; what does not survive is the belief that they changed the shape. Text assembled from material that is owner-safe by construction leaves no free-form string to inspect, so the class cannot be **produced** rather than being reliably caught. The pattern to copy already ships upstream: a plain-register rendering is produced **once** at the ratification gate, pinned to the content's hash, and every consumer **quotes** it rather than composing its own — nothing downstream judges readability because nothing downstream may invent wording. **The diagnostic, stated so it can be checked rather than felt:** a check suite growing at roughly **one member per incident** is the tell that the remedy is on the DETECT side when it should be on the CONSTRAIN side; the **slope is the instrument, not the level**, and the suite is deliberately given no ceiling here. Measured 2026-07-28: **134 `check-*.sh` of 176 scripts**, up 2 that day — one per story, which is the tell firing on this repository's own work. When a remedy-shape check is built, it **binds proposals, never captures** (filtering at capture would delete the recurrence signal that is the best instrument available) and — **because such a check is a judgment** — it **rides an existing gate rather than becoming a new blocking hook**, otherwise the remedy for too many enumerated gates is a new enumerated gate. **The discriminator is mechanical-vs-judgment, and it is what tells the two cases apart** (scoped 2026-07-28 from triage #857, after the clause's first form dropped the "is a judgment" premise and read as a blanket ban): a check deciding a **mechanical fact** — an inventory diff, a membership test, a shape assertion with no reading of intent — is an ordinary `scripts/check-*.sh` and needs no special siting; a check that must **read a proposed fix and rule on it** may not become an automated blocking member, and rides a gate where a human is present. **This repository's gate, named so it is not re-derived:** the loop's `test_cmd` (`~/.tanuki/scenarios/writing-assistant.scenarios.json`, key `loop.test_cmd`) globs `scripts/check-*.sh`, skips six named exclusions, and runs each as `sh "$t"`, failing the iteration on any non-zero exit. - **Capability evidence is OBSERVED, and the fixture corpus is the coverage instrument** (engine-wide; added 2026-07-30 from triage #940): `CAPABILITIES.md` answers *is capability X implemented, and evidenced by what?* for a reader who will not read the code, and its own preamble promises that *"if the capability breaks, its evidence fails, and the manifest fails with it."* **That promise was falsified, and this clause is what makes it true.** The falsifying instance (#933): Terrain's Journey material rendered nothing for days while the `terrain` row stayed `implemented` and its evidence check kept passing. **The mechanism, measured at triage rather than inferred:** the committed fixture every terrain check tests against carries `gloss.journey_renderings: 0` and `gloss.journeys_requested: []` (`scripts/fixtures/terrain/screen-map.json`), so a journey assertion would have been **vacuous even if written** — the gap is not a missing assertion per feature, it is that nothing notices the corpus never exercises the thing. This matters because the manifest is a **cross-repository** claim surface: an upstream sitting already began a duplicate build from prose (#805), which is why a row that can be silently wrong is worse than no row. Three clauses bind. **(a) Observed effect, not source shape.** A row's `evidence` check must assert an effect the capability produces *in a run* — not only that the source declares it. A grep over implementation text evidences that code exists, which is the existence-versus-standing split one level down: text asserting a capability is not the capability firing. **(b) A failed corpus precondition reports DISTINCTLY.** Where an assertion depends on the corpus containing material of some kind, the absence of that material is reported as its own state — neither a pass nor a failure. A vacuous pass is the #933 failure mode exactly, and a hard failure on an unrelated corpus would make the check unusable; three-valued reporting is the same discipline the absence rules already carry (`cannot-determine` is not `absent`). **(c) The fixture corpus must exercise every declared capability, and the check for that is ONE member.** A capability whose fixture material is empty is a coverage gap declared *at the fixture*, where a single mechanical assertion sees all of them at once — and this is the clause that fires on #933 without anyone having remembered the feature existed. **Why this shape and not one observable per feature** — the shape #940 proposed: the served architecture line makes *"a check suite growing at roughly one member per incident"* the checkable tell that a remedy sits on the DETECT side when it belongs on CONSTRAIN, and the adjacent instrument was ratified **selective on silent failure mode** three days earlier precisely because *"registering everything kills the cadence"* (*owner decision record — 2026-07-28 (constrain generation rather than improve post-hoc detection)*; *owner decision record — 2026-07-29 (register a hypothesis only where its failure mode is silent)*; both consulted at the pin, coverage partial). One-per-feature adds a member per incident by construction, against a suite this spec has just put under a **slope** budget. So the completeness promise binds at the granularity a single instrument can hold — the declared capability — and not per feature. **The gap this accepts, stated rather than assumed away:** manifest rows are capability-level, and a marker, a row kind or an exit line sits below that granularity — #933's own defect did. **Watch trigger, which is what would earn the per-feature form:** a second #933-class regression in a feature whose absence the fixture corpus cannot express.
